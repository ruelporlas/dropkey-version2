# DropKey Version 2

DropKey V2 currently implements the admin data-management layer, private versioned ZIP release storage, license issuance/activation, expiring download links, and a versioned REST API with a portable PHP client.

## Requirements

- WordPress 6.4+
- PHP 7.4+
- HTTPS for licensing endpoints and protected downloads
- PHP write permission for the configured private package directory
- A directory configured outside the web server's public document root for ZIP packages

## Admin screens

Activation creates a **DropKey** menu with:

- **Products:** create/edit products and publish or archive them.
- **Tiers:** create/edit product tiers, descriptions, and per-tier maximum website activations.
- **Billing Options:** configure free, one-time, monthly, and yearly options, prices, currency, and status.
- **ZIP Releases:** upload versioned ZIP files and set release notes/status.
- **Licenses:** manually issue licenses for published products/tiers, change license status, view and deactivate active website activations, and generate protected download links.

A license key is shown only when issued. DropKey stores the SHA-256 hash and a short prefix, not the full key. Issuing a license from the admin is a manual grant, not proof of a completed payment.

## Private package storage

DropKey does not store packages in the WordPress Media Library. The default path is a sibling directory named `dropkey-v2-private` next to the WordPress installation directory. **Do not assume that this path is outside your public document root.** Configure an absolute path outside the public web root through `wp-config.php` or a site-specific plugin:

```php
add_filter( 'dk2_private_storage_path', function () {
    return '/absolute/path/outside/the/public/web/root/dropkey-v2-private';
} );
```

The directory must be writable by PHP. DropKey adds an `.htaccess` denial file and `index.php` as defense in depth, but those files do not protect Nginx or every server configuration. Confirm server-level access is denied before storing real packages. ZIP uploads are checked for a ZIP extension/signature, saved privately, and recorded with SHA-256 digest and file size.

## Licensing API

Base URL: `https://your-dropkey-site.example/wp-json/dropkey/v1`

- `POST /licenses/activate`: JSON `license_key`, `site_url`
- `POST /licenses/deactivate`: JSON `license_key`, `site_url`
- `POST /licenses/validate`: JSON `license_key`, optional `site_url`
- `POST /products/{product-slug}/updates`: JSON `license_key`, `site_url`, `current_version`
- `GET /downloads/{token}`: protected ZIP delivery for a token generated by DropKey

The API uses the license key as a bearer credential and must be used over HTTPS. The client keeps TLS verification enabled and does not embed an administrator secret:

```php
require_once plugin_dir_path( __FILE__ ) . 'includes/dropkey-license-client.php';

$dropkey = new DropKey_License_Client( 'https://your-dropkey-site.example', 'your-product-slug' );
$result = $dropkey->activate( $license_key );

if ( is_wp_error( $result ) ) {
    // A transport error is not proof that a license is invalid. Offer retry.
}
```

Copy `sdk/dropkey-license-client.php` into the plugin you sell (and update the include path in your plugin). The REST update-check endpoint can issue a protected download link for a newer published release. A complete integration into WordPress's Plugins update screen is not included yet.

## Implemented boundaries

These milestones do **not** implement checkout, PayPal/Stripe payments, order/subscription records, payment webhooks, automatic customer emails, customer-facing account pages, subscription lifecycle automation, rate limiting, or the complete WordPress plugin-updater UI. Do not use manual license issuance as evidence of payment. Before production use, review the security and concurrency behavior, configure server-level private storage, and run WordPress integration tests.

## Verification

GitHub Actions runs PHP syntax checks on PHP 7.4, 8.0, and 8.3. A passing syntax check is not a substitute for testing in a real WordPress environment. Verify activation/schema upgrades, each admin CRUD path, upload/path safety, license activation limits, invalid/suspended/expired keys, token expiry/download caps, and all REST responses before production use.
