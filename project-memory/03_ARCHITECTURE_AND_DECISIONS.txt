DECISION LOG

Date: 2026-10-14
Decision: Use Product → Tier → Billing Options as the product-offering model.
Context / problem: The user wants multiple licensing tiers and needs the activation limit to be configurable per tier, while supporting free, one-time, monthly, and yearly offerings.
Options considered: (1) Each tier has billing options; (2) each tier-and-billing combination is treated as a separate plan.
Reason for choosing: The user asked to choose the simpler option and agreed to the recommendation. Keeping tier settings together avoids duplicating tier-level settings such as activation limits across billing variants.
Consequences and trade-offs:
- A product can have multiple tiers.
- A tier owns tier-level entitlements, including its configurable maximum active website count.
- Each tier can enable applicable billing options (free, one-time, monthly, yearly).
- Prices and billing cadence belong to their respective billing options.
- Tier names and activation counts are not fixed by this decision.
Status: accepted.
Evidence or related files: project-memory/04_REQUIREMENTS_AND_RULES.txt, DK-008 and DK-010.

Date: 2026-10-14
Decision: Implement Milestone 4 commerce using hosted payment-provider flows and a provider-independent order/entitlement service.
Context / problem: The MVP needs checkout and paid fulfillment without storing payment-card details, while keeping gateway-specific API details out of core order/licensing logic.
Implementation choices:
- Public catalog and checkout are exposed through the `[dropkey_store]` shortcode and a public checkout handler/REST endpoint.
- Stripe uses hosted Checkout sessions; recurring billing options use subscription Checkout mode and inline price data. Stripe webhook signatures and timestamps are verified locally.
- PayPal one-time checkout uses order approval plus server-side capture and amount/currency comparison. PayPal recurring options reference a plan ID created in PayPal; webhook signatures are verified using PayPal's verification API.
- Core orders, subscription records, payment-event idempotency, individual provider payment references, and encrypted email queue entries are separate tables.
- A successful provider event must match an order and its amount/currency before paid fulfillment. Refunds suspend licenses; dispute events mark orders disputed and suspend licenses.
- License issuance, protected download token creation, and encrypted fulfillment-email queueing are part of one database transaction.
- Email queue content uses authenticated AES-256-GCM encryption, WP-Cron retries, and administrator retry controls.
- Admin-managed cancellation is scheduled for the end of the paid period; Stripe cancellation is scheduled remotely, while PayPal cancellation is sent when the paid-through date arrives.
- Public checkout attempts are rate-limited per client IP and email. Authenticated provider API requests disable redirects and verify TLS.
Consequences / limits: Provider credentials remain in WordPress options, never source control. PayPal recurring plans must be created manually. WordPress runtime, provider sandbox events, mail delivery, and production concurrency/security behavior still require end-to-end testing.
Status: implementation committed; static CI and network-free contract tests pass; runtime behavior not yet verified.
Evidence: https://github.com/ruelporlas/dropkey-version2/actions/runs/38593681895 and project README.

2026-10-14 — Milestone 2–3 implementation decisions recorded from the current source
- Database schema version: 3; added release, license, activation, and download-token tables while preserving products, tiers, and billing options.
- Admin screens are registered under DropKey and use manage_options capability checks, action nonces, and admin-post handlers.
- License keys and download tokens are stored as SHA-256 hashes; the full license key is shown once during manual issuance.
- Site activation uses the submitted site URL with trailing slash removal. The URL canonicalization policy remains a technical choice to revisit if testing identifies mismatch cases.
- Download links expire after 48 hours and allow five successful downloads each. The package digest is checked before streaming.
- Package storage defaults to a sibling directory, but upload handling rejects paths inside ABSPATH or the detected DOCUMENT_ROOT; hosts must configure a writable absolute private path and verify server-level access restrictions.
- The REST client requires HTTPS and enables TLS certificate verification. License keys are bearer credentials; rate limiting and broader production hardening remain outstanding.
- Status: implementation choices in current source, not yet runtime-verified.

PAYPAL PLAN PROVISIONING DECISION — 2026-10-15
Decision: PayPal subscription plan provisioning is handled inside `PayPal_Gateway`, not as a manual administrator prerequisite.
Context: Product, tier, and billing option setup should remain gateway-neutral; administrators should define price and interval in DropKey rather than switching to PayPal to create each provider plan.
Implementation: On the first PayPal checkout for a monthly/yearly billing option without a stored plan ID, create a PayPal catalog product and active fixed-price recurring plan using the selected Sandbox/Live credentials, then persist the returned plan ID. PayPal request IDs are derived for retry idempotency. Changes to billing type, price, or currency clear the local plan reference so a matching plan is created at the next checkout.
Consequences: PayPal API credentials must be configured before paid PayPal checkout can provision a plan. Provider calls are deferred until checkout, so saving a billing option does not depend on PayPal availability. Existing subscriptions are not migrated when billing terms change.
Status: source committed; PHP syntax CI passed on PHP 7.4, 8.0, and 8.3 for code commit `a26c21b81d53b0d6c457c8d98a3e4eba6c59360d` (https://github.com/ruelporlas/dropkey-version2/actions/runs/38658721423). WordPress/PayPal Sandbox runtime verification remains pending.


Decision — Structured operational logging (2026-10-15)
- Add a dedicated `dk2_logs` table rather than relying only on host PHP logs, so authorized administrators can inspect DropKey events inside WordPress Admin.
- Logger class: `includes/class-logger.php`; schema version 8; log levels debug/info/warning/error/critical; per-request correlation ID; 30-day cleanup; logging enabled by default and configurable on the Debug Logs screen.
- Context redaction and bounded field sizes are applied before persistence. The logger must never store provider credentials, auth headers, passwords, license keys, raw request/response bodies, customer email addresses, or complete checkout URLs. If the log table write fails, fallback is a generic PHP error_log message to avoid recursive logging or leaking context.
- Admin log viewer requires manage_options, supports level filter/pagination and clear-all. This feature is source-implemented but WordPress runtime verification remains pending.
